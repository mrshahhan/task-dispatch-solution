# Заметки

## Что изменилось бы при нескольких экземплярах с общей БД

Сейчас идемпотентность и счётчики лимита лежат в памяти процесса, а атомарность держится на том, что Node.js выполняет проверку лимита и запись синхронно. С несколькими экземплярами это перестаёт работать:

- **Гонка за последнее место в лимите.** Два экземпляра одновременно прочитают «заняло 2 из 3» и оба посадят заказ в филиал. Проверка и запись должны быть одной атомарной операцией в БД: строка счётчика `(branch_id, date)` и `UPDATE ... SET assigned = assigned + 1 WHERE assigned < daily_limit` с проверкой числа затронутых строк. Если место не занято, берём следующего кандидата. Либо транзакция с `SELECT ... FOR UPDATE` по строке филиала на дату.
- **Идемпотентность.** `Map` по `orderId` заменяется таблицей распределений с уникальным ключом `order_id`. Запись распределения и инкремент счётчика делаются в одной транзакции, а при конфликте по ключу (`INSERT ... ON CONFLICT DO NOTHING`) возвращается уже сохранённая строка. Тогда дубли, пришедшие одновременно на разные экземпляры, не займут лимит дважды.
- **Счётчик или пересчёт.** Либо хранить счётчик, либо считать `COUNT(*)` по таблице распределений с индексом `(branch_id, day)`. Счётчик быстрее, но его нужно менять строго в той же транзакции, что и распределение. День в таблице нужно хранить явно (дата по Алматы от `createdAt`), чтобы не пересчитывать часовой пояс.
- **Порядок блокировок.** Если транзакция трогает несколько филиалов (выбранный, затем запасной), блокировки нужно брать в одном порядке (например, по `branch_id`), иначе возможны взаимоблокировки.
- **Кеш и чтение.** Данные филиалов и заказов читаются из БД (или кешируются с инвалидацией), а не из JSON при старте: изменение `active` или `dailyLimit` должно быть видно всем экземплярам.
